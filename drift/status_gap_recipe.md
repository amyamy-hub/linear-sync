# Status 选项差集检查 · 操作配方（⛔ 不是脚本，是配方 —— 原因见文末）

用途：回答一句话 —— **"Linear 里能被拖到的档，Notion 的 `Status` 白名单是不是全覆盖？"**
不覆盖 ⇒ 谁把工单拖到那个档，同步就 400 `failed`、**页面数不变**、覆盖式无告警 ⇒ 一行既没被覆盖也没人知道。

## 三步（全部只读）

1. **读 Notion 白名单** —— 用数据源 schema 读接口取 `Status.options` 的**名字与 option id**（⛔ 别用 SQL，SQL 只给在用的值，不给白名单）。
   本库数据源：`collection://3e230d6b-1b59-81e3-b565-000b5fc560ed`
2. **读 Linear 侧"可用档"** —— ⚠️ **必须两个来源求并集，⛔ 任何一个都不够**：
   - `list_issue_statuses(team=Amy-agent)`
   - `list_issues()` 里**实际在用**的 `status` 值
   实测过的理由（09-24 10:0x 北京）：工作流接口回 5 条，⛔ **连正在被一张工单使用的 `Backlog` 都没列出来** ⇒ 它不是全集；反过来 `list_issues` 只给"已用过的档"，不给"可拖但没在用"的档 ⇒ 两者求并才敢用。
3. **报差集** = (Linear 并集) − (Notion 白名单)。非空 ⇒ 亮灯；同时报"哪一档只在其中一个来源出现"，那种档要单独确证⛔ 不许直接加。

## 故障注入（不配这个，这条检查本身就是一盏可能瞎的灯）
- **该亮的必须亮**：临时把某个 Notion 没有的档名写进比对集 ⇒ 期望非空差集。
- **该不亮的必须不亮**：只比同名不同色的两版 ⇒ 期望空差集（⛔ 颜色不是判据）。
- **量具自己**：把 Linear 两个来源任意一个换成"只查到的那 5 条"重跑 ⇒ 差集会**变小**（少了 `Backlog`）⇒ 这就是"单来源会漏"的现场证明，跑一次就记住。

## 改表前置（差集非空时怎么补，⛔ 不取基线别动手）
`ALTER COLUMN "Status" SET SELECT(...)` 是**整表替换**语义 ⇒ 先取基线（当前全部 option 的名字+颜色+**option id**），执行后回读两件事：① 旧 option 的 id 与基线**逐字符相同**（没被重建）；② 各行 `Status` 与 Linear 现值**逐行一致**（没被清空）。
另外 ⚠️ `notion-fetch` 会返回 `-32603 / did not complete` 这种**假失败**（本轮连吃三次，第四次成功）⇒ 重试即可，⛔ 别把它读成"库连不上"。

## 为什么这是配方而不是脚本
`tools/drift_check.py` 能做成本地脚本，是因为用户为 Cloudflare 单独铸过一把 token 落在本机。
而 **Notion 与 Linear 的凭据只存在 Cloudflare 的 secret 里，本机没有**（secret 按设计永不可读）。
⇒ 这条检查现在只能由**带着 Notion/Linear 连接器的客户端**（Qoder / WorkBuddy 等）按上面的配方执行，⛔ 不能做成 `python tools/xxx.py` 跑起来。
⇒ 要实体化，前置条件是用户愿意落一把 Notion/Linear 的只读 key 到本机 —— 那是**新增长期凭据**，与"给第二家客户端铸 CF 只读 token"同一类决定，⛔ 别顺手做。
