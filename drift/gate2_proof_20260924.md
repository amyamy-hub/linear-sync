## 一、此前为什么判“不可判”（两条理由仍然成立）

1. `/versions/{id}` 不返回任何字节（`resources.script` 只有 `etag / handlers / last_deployed_from`）。
2. `etag` 64 hex = 256 bit，git blob = 40 hex = 160 bit ⇒ 量纲不同，⛔ 不可对撞。

被推翻的是第三条推论：**“拿不到字节”是错的**，所以“不可判”也不是终局。

`GET /accounts/{account_id}/workers/scripts/linear-sync/download`
→ `multipart/form-data`，唯一部件 `name="index.js"`，即线上字节。

采样 2026-09-24T15:17:01Z（WebCrypto 求摘要，与本地 Python hashlib 是两支实现）：

## 三、⛔ 这个端点的 `version_id` 参数是死的（本轮最重要的量具教训）

15:18:08Z 连打四发，`?version_id=` 分别取 **#13 `5e011838`／#9 `2fc04c35`／未部署的 #10 `a7ba0f39`／不带参数**
⇒ **四发字节完全相同**（blob 均为 `3a698aff…`）。而 #9 的 `etag` 已知是 `5d4e6aad…` ≠ #13 的 `b5cc1a50…`
（15:14:01Z 现读）⇒ 若参数生效，#9 那一发**不可能**与 #13 同字节。

⇒ 判据（进“探针返回 0 必须有阳性对照”同族）：**重复读数全等，只有在你构造过一个“必然改变输出的输入”之后，才算证明了这个量具是稳定的**；
否则你看到的“稳”可能只是“它根本没响应输入”。这里正是后者。

因此 `/download` 给的是**脚本槽位当前内容**，不是“某个版本的内容”。

## 四、那么“槽位字节”凭什么等于“服务字节”——升格条件

链条三读，缺一不算证：

1. `GET .../deployments?per_page=100` → `deployments[0].versions[0].version_id` = `5e011838…`（服务中 = #13）。
2. `GET .../versions/5e011838…` → `etag = b5cc1a50dc085ecd8cdaa7c19e480ca99ac27b063c6bc193dc1a37f59aafd05c`。
3. `GET .../workers/scripts` → 槽位 `etag = b5cc1a50…`（与第 2 条**全等**），`modified_on = 2026-09-23T16:53:57.758464Z` = #13 `created_on`。
4. `/download` 槽位字节 → blob == 仓库 blob。

⇒ **第 2↔3 步的 etag 等式是升格用的桥**：槽位内容与服务版本的产物指纹一致，才允许把第 4 步的哈希结论读成“线上服务代码 == 仓库”。

**失效场景（已知会破）**：发生“上传未部署”时，槽位会占住未部署的字节，此时 `/download` 与 `/scripts.etag` 一起漂走，
而 `/deployments[0]` 仍指旧服务版。⇒ **检测器规则**：
`scripts.etag == deployments[0]→version.etag` 不等 ⇒ 闸门 2 ⛔ 不许用 `/download` 下判，改判“服务字节不可证”。
该检查目前**尚未**进 `tools/drift_check.py`（待办）。
